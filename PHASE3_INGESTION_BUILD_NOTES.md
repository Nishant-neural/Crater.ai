## What changed (file paths, edits not rewrites)

### 1. Postgres replaces SQLite (`docker-compose.yml`, `backend/db/models.py`, `alembic/`)
- `docker-compose.yml`: `DATABASE_URL` is now wired for the gateway
  (monolith) and the ingestion service + worker:
  `postgresql+psycopg://crater:crater@postgres:5432/crater`
  (`+psycopg` because `psycopg[binary]` v3 is the installed driver;
  bare `postgresql://` would look for psycopg2, which is not
  installed). The "provisioned but NOT wired" note is replaced.
- `backend/db/models.py`: new `IngestionJobProgress` model
  (`ingestion_job_progress`: `job_id` PK, `progress` JSON,
  `updated_at`). `job_id` is a plain key, not a foreign key — the
  worker writes progress with its own session and must never fail a
  job on FK ordering.
- `alembic/` (new, via `alembic init` + edited `env.py`) +
  `alembic.ini`: Alembic replaces `backend/db/migrations.py`
  (deleted; zero importers verified by grep). `env.py` takes the URL
  from app settings (`DATABASE_URL`), never from the ini, so compose
  migrates Postgres and local dev migrates SQLite.
  `alembic/versions/3f515989a9f9_initial_schema_postgres_move_ingestion_.py`
  is the autogenerated initial schema (37 `create_table`s, including
  `ingestion_job_progress`).
- No SQLite→Postgres data migration exists or is wanted (contracts
  §8.2): the next ingestion round re-ingests from PDFs against
  Postgres. `session.init_db()` (`create_all`) is unchanged.
- NOT done: the contracts §8.2 composite `(revision_id, chunk_type)`
  index could not be added — `chunks` has no `revision_id` column
  (revision is reached via the `Document` join). Adding the column
  is a schema change for a later step, not silently invented here.

### 2. Celery + Redis replaces BackgroundTasks (`backend/ingestion/celery_app.py`, `tasks.py`, `backend/api/routes/ingestion.py`, `backend/config.py`)
- `backend/ingestion/celery_app.py` (new, minimal): broker Redis db 0,
  result backend db 1 (derived from the broker URL unless
  `CELERY_BROKER_URL` / `CELERY_RESULT_BACKEND` are set), JSON
  serializers, UTC, `task_track_started`, default queue `ingestion`,
  `include=["backend.ingestion.tasks"]`.
- `backend/ingestion/tasks.py` (new): `run_ingestion_job` — the former
  `_run_job_background` from the routes module, moved verbatim (same
  session handling, stage strings, mark-failed behaviour), plus a
  re-raise after the failure is recorded so Celery retries 3x with
  exponential backoff (`autoretry_for=(Exception,)`,
  `retry_backoff=True`, `max_retries=3`). A retry resumes from the
  Postgres progress row, never a whole-manual restart.
- `backend/api/routes/ingestion.py` (edited): all three BackgroundTasks
  call sites (`POST /ingest`, retry, lazy-ingest) now dispatch via
  `_queue()` → `run_ingestion_job.delay(job.id)`. A broker outage is
  a loud 503 naming Redis/Celery. `_run_job_background` is deleted
  from the routes module (it lives in `tasks.py` now).
  `_job_response` gains the contracts §3.2 `progress` object, built
  from the Postgres progress row + stored rows (document page count,
  chunk count, FailureMode-row count). `table_rows_parsed` is the
  FailureMode-row count for the revision — the deterministic table
  parse persists one FailureMode row per parsed failure mode
  (`persist_machine_knowledge`), so it is the checkable row count
  until the dedicated `table_rows` table (contracts §3.5) lands.
  `table_rows_total` is 0 (nothing tracks it yet, not invented).
- `backend/config.py`: `celery_broker_url` / `celery_result_backend`
  (both default `""` = derive from `redis_url`). `.env.example`
  documents them and the Postgres compose URL.

### 5. Ingestion service container (`docker/ingestion/Dockerfile`, `docker-compose.yml`, `backend/ingestion/app.py`, `backend/ingestion/readiness.py`)
- `docker/ingestion/Dockerfile` (new): mirrors the gateway Dockerfile
  (Python 3.12-slim, tesseract, `uv sync --frozen`, copies
  `backend/` + `alembic/`), `/health` healthcheck. CMD runs
  `alembic upgrade head` then `uvicorn backend.ingestion.app:app`.
  Still builds the monolith tree for now (see §7 coupling note).
- `docker-compose.yml`: `ingestion` service (internal-only, no
  published port — the gateway still serves the public /v1/ surface
  from the monolith until the later splits) + `ingestion-worker`
  (same image, `celery -A backend.ingestion.celery_app:celery_app
  worker`). Both get `DATABASE_URL`, `QDRANT_URL`, `REDIS_URL`,
  `CELERY_BROKER_URL` (db 0), `CELERY_RESULT_BACKEND` (db 1).
- `backend/ingestion/app.py` (new): FastAPI app serving ONLY the
  ingestion-owned routers — `ingestion`, `products`, `machine_knowledge`,
  `mode_b` — under `/v1/` plus the legacy unversioned alias, exactly
  as the monolith mounts them today. `/health` (liveness only),
  `/ready` (see below), request-ID middleware, standard error
  envelope handlers. No diagnosis / twin / gateway routes mounted.
- `backend/ingestion/readiness.py` (new): `/ready` checks Postgres
  (`SELECT 1`), Qdrant (collection exists + answers), Redis (PING on
  broker db 0 and result backend db 1), Celery (at least one worker
  answers `control.ping`). Any failure → 503 with a per-dependency
  breakdown naming the failed check. No silent fallbacks.

- **Diagnosis-side cross-service reads** — verified to REMAIN

    `MachineKnowledgeModelSnapshot` (+ `Product`, `Revision`)

  - `backend/retrieval/hybrid.py:20`, `bm25.py:18` read `Chunk` /
    `Document` / `Revision` rows (retrieval's own tables after the
    split; the `Chunk`/`Document` rows are ingestion-written).
  - `backend/diagnostics/agent.py:101,117`, `graph.py:62`,
    `routes/diagnostics.py:33,69,1002,1040`, `routes/query.py:16`
    import `backend.db.models` / `backend.knowledge.repair_cases`.
  - `backend/diagnostics/learning.py:30,34`, `fleet.py:32`,
    `downtime.py:22`, `pm.py:19` — DEFER-retained surfaces reading
    their own models today.
  - Reverse direction: `backend/api/routes/mode_b.py:18` imports
    `start_session` from `backend.diagnostics.agent` — the Mode B
    diagnose endpoint must become an HTTP call to diagnosis-agent
    in that step. The ingestion image therefore still builds the
    monolith tree.
- **TableRow as a table** (contracts §3.5): `TableRow` exists only
  as the in-memory dataclass in `backend/ingestion/table_parser.py`
  (1,190 lines, kept as an internal module — verified: imported
  only by `pipeline.py`, scripts and tests; no service, no
  `POST /v1/tables/parse`, and the contract test asserts the path
  does not exist). Persisting parsed rows to a `table_rows` table
  is a separate data step.
- **Indexing/embedding** stays in ingestion, untouched
  (`pipeline.py` upserts via `vector_store`; ingestion is the sole
  Qdrant writer). Retrieval search stays in diagnosis-agent.
- **Chunk sizing split (P-02)** and Docling/TableFormer are Phase 2
  work, not this step.
- **At-least-once delivery:** Celery may redeliver a job (worker
  crash, retry endpoint on a still-queued job) and two runs of the
  same job are not fenced — the pipeline's resume logic makes a
  second run mostly a no-op (completed pages/chunks are skipped),
  but concurrent execution has no lock. A worker-side claim
  (`processing` + owner + heartbeat) is future hardening, not
  built here.
